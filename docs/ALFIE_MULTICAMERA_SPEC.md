# Alfie multi-camera Program / Preview design (Multiview console)

**Status:** implementation-ready design for R2; no multi-camera implementation is present at `aded5a3` (release build 3). This document is authoritative for R2 over the older S2/S3 dual-HDMI briefs. The console direction (Option 3 · Multiview) and the up-to-four-input layout goal were recorded on 28 Sep 2026 (SPEC-MV); where this text and a Trello card disagree, update the card or this document so they match. It does not certify R1 or R2 for release. R1 has positive manual feedback, while its full soak and readiness gates remain open.

## Product contract

Two independent camera inputs, **A** and **B**, run at once. One is **Program**, the camera currently routed to Alfie's single downstream feed. The other is **Preview**, the operator's next shot, prepared for a deliberate **Take**. (Earlier drafts called this role "Stage"; Stage now only names a `CaptureProfilePolicy` source profile.) The sole output is the existing Program Display **or** the existing single virtual-camera route, connected to one ATEM input. The ATEM handles any external audio and its own switching; Alfie does not ingest, mix, or claim to control audio or know ATEM tally. “Program” means Alfie's routed picture, never a claim about the ATEM's on-air selection.

Preview taps, Detect, preset, Push/Pull, Manual, Pan, and Return to Wide affect Preview alone. They never cut Program. With two channels, Preview is always the other channel; the operator cannot select the live channel as Preview. The N-input rule is in *Input capacity* below. **Edit Live** is a separate, conspicuous operator action and state with a persistent `Editing live A/B` indication; commands created there explicitly target the live channel. Take exchanges the two roles atomically only from an already fresh, legal Preview render. Both channels retain their state through a Take; returning to a channel resumes its current mode and motion, not a reset or copied shot. A successful Take exits Edit Live and binds the controls to the new Preview. No second output, second CMIO device, direct SDI, speech, physical hardware, or T5a easing rewrite belongs to R2. The R2 technical release ships exactly two running inputs; a third and fourth input are gated follow-on work (see *Input capacity*), not an R2 exclusion.

The show output format is frozen once per show: the existing `ShowStandard` 1920×1080 at 50, 60000/1001, or 60 fps (and existing portrait profile where supported). Multi-camera runs only in Stage format (see *Format scope*), so A and B both use the `CaptureProfilePolicy` Stage profile and each must supply the frozen show rate; no quiet 30 fps substitution, resolution change, or invented sharpness. Delivered source dimensions, rather than advertised active format, drive legal crop and detail messages.

## Format scope: Stage vs Webcam

Alfie has two cinematic formats (`ShotComposer.Config.CinematicFormat`), and this whole design applies to **Stage only**.

| | Stage | Webcam |
| --- | --- | --- |
| Main view | Multiview console (this document) | The traditional single-camera view: wide source + crop and the existing operator pill, unchanged |
| Inputs | Up to four slots; R2 ships two | One camera; no Preview, Take, Edit Live or input row |
| Capture profile | Prefers 3840×2160; every format must run at the show rate exactly, or the camera is refused | Prefers 1920×1080, then 720p-class; uses the show rate when any HD format has it, otherwise the webcam's fastest HD format at its own rate (reason `webcamBelowShowRate`, shown in the capture status line) |

`ConsolePresentation.resolve(for:)` is the single mapping from format to view. Switching format swaps the whole console, so it is refused while a multi-camera show is running; the operator stops the show first. A single-camera session switches as it does today. A Webcam-mode camera running below the show rate is paced into the output at the show standard, so the virtual camera repeats frames and the existing frame-rate-match bring-up check shows a warning. That is accepted for video calls and never applies to Stage.

## Existing seams to respect

At this revision `CameraManager` is `@MainActor` and holds one `AVCaptureSession`, `PersonDetector`, `ShotComposer`, `CropEngine`, command dispatcher, latest wide and rendered buffers, last-good crop/buffer, and `ProgramOutputManager`. Its capture delegate has a one-frame `CaptureFrameProcessingGate`, then hops to MainActor. `CropEngine.renderCrop` uses a static serial queue. `OperatorCommand.Target` has only `.cameraA` and `.session`, with one epoch. `ProgramOutputManager` owns a single active display/virtual-camera sink and freezes `ShowStandard`; `DisplayOutputSink` resolves one persisted display ID and can request route fallback. The XPC protocol and extension expose one frame stream. These are extraction points, not two-instance-ready APIs.

Avoid a general media graph. Use `ChannelID` (`A`, `B`), a per-channel controller (an extracted `CameraManager` is acceptable), `ShowCoordinator`, a bounded scheduler, and `OutputRouter`. Preserve the existing single-camera behavior before enabling B.

| Owner | State and responsibility |
| --- | --- |
| Each `Channel` | Stable ID and source identity; one capture session and serial configuration executor; capture generation; latest capture mailbox; detector and observation generation; identity gallery and subject lock; composer; crop engine; operation mode; preset and one-rung zoom move; manual point; pan phase; command epoch and shot revision; last-good rendered buffer/crop and health. |
| `DeviceDirectory` | Discovery and exclusive claims on physical device unique IDs. Persistent preferred assignments are requests, not authorization to start. |
| `ShowCoordinator` | Show lifecycle and rate, two channels, Program/Preview role IDs, UI command target, explicit live-edit state, admission and aggregate health. |
| Scheduler | Bounded capture, perception and render admission; fairness and priority based on roles; no unbounded task or buffer queues. |
| `OutputRouter` | Sole owner of `ProgramOutputManager`, one active sink, output clock and Take serialization. Only this component can change the routed channel. |

The output manager must start/end the show standard **once per show**, not once per channel. A channel cannot connect XPC or open a Program Display. Camera permission, extension activation, output settings, and diagnostics aggregation remain show-wide.

## Message and time model

An immutable capture packet carries `channelID`, `sourceGeneration`, monotonic per-channel `captureSequence`, source presentation time, host arrival time, delivered dimensions, and a strong reference to the source `CVPixelBuffer`. A detection result additionally carries observation generation/ID and the capture sequence used. A render packet carries source generation, capture sequence/time, `shotRevision`, command epoch at its snapshot, normalized legal crop, output dimensions, render-complete host time, source health, and a strong reference to its rendered IOSurface buffer. Channel IDs prevent cross-lane completion; generations reject prior start/stop/rebind work; shot revision rejects a render from before a discrete preset/mode/zoom/manual target/subject-lock intent change. Acquisition, retarget, unlock and recovery transitions increment it; ordinary tracking motion and interpolation do not. The per-channel command epoch cancels superseded command effects; it is not the output-frame sequence. A UI control-target revision invalidates queued UI intents created before entry/exit of Edit Live or a Take but does not invalidate already-running channel work or cause a Take.

All ages use the same monotonic host clock. Source PTS is retained for measurement and ordering within its generation; it is **not** compared directly with host time and is **not** passed as a discontinuous downstream clock across cameras. Output frames use the single output clock's monotonic presentation timestamps, including a repeated hold frame. A Take must never move that clock backward, duplicate a tick, or allow a late old-Program render to appear after the new role is committed. The router keeps a route generation; each enqueued send is tagged with it and checked at final send. Within a generation it rejects out-of-order capture sequences and source timestamps; repeated last-good holds are explicit repeats, not new source frames. The output sink retains the presented surface until replacement is safe, as today; the router also retains Preview's prepared render until Take commit or invalidation. No raw capture buffer may be sent on render failure. A sink's `sendFrame` acceptance is the software commit boundary: enqueue the qualifying frame on the next output tick, then exchange logical roles and publish the Program UI snapshot together. If the sink refuses or the bounded transaction deadline passes, keep the old roles and report Take failure. Display/CMIO handoff and ATEM acquisition are asynchronous and cannot be asserted as physically atomic or acknowledged by this API; verify the downstream picture in hardware QA. The Program pane follows the committed router frame, not an optimistic button press.

**Provisional, configurable initial Take thresholds, to calibrate on the rig:** at click, an already prepared Preview render must have completed within 2 show-frame periods, derive from a source captured within 4 frame periods, match the current source generation and discrete shot revision, have legal crop/output geometry and a healthy source, and not be a held/repeated frame. If any check fails, reject this click immediately; `Preparing B` means Take is disabled until a qualifying render arrives, **not** an armed future auto-cut. An admitted Take reserves that exact packet, revalidates it and the roles/revision at the next output tick, and expires if not committed within 2 frame periods of the click. It never substitutes a later packet without a new click. A channel in an ongoing one-rung zoom or pan may be taken: the qualifying frame must reflect the current move's revision and interpolated crop. Starting or reversing a move increments the shot revision; interpolation ticks do not. These timing numbers are calibration gates, not demonstrated performance claims. The hard invariant is that Take never admits an old generation/revision, illegal geometry, or held frame.

## Lifecycle and routing state machine

Start from `stopped`, no claimed device, no live route, and no auto-live from persisted settings. Read preferred A/B device IDs and capture profiles; show them as proposals. Validate camera permission, distinct device IDs, present devices, compatible formats at the frozen show rate, and the chosen output destination. Claim each device exclusively before configuring it. Start A first and prove its legal fresh rendered frame can reach the selected output sink; only then assign Program A and expose a live route. The initial A frame has the same legal-geometry/freshness/epoch checks as a Take candidate. Then start B independently as Preview; B discovery/start cannot alter the live route. A running show with only A is a truthful degraded state; B failure never aborts A. If A cannot deliver a legal frame, report no live source and do not substitute B or silently promote Preview.

Each channel transitions `unassigned → configured → starting → running → faulted/stopped`; start/stop/rebind increment its source generation and retire queued capture, detection, render, and command completions. Device configuration, `lockForConfiguration`, and `startRunning`/`stopRunning` execute on that channel's serial executor, never as blocking MainActor work. Short role, command-admission and UI state transitions remain on MainActor or one explicit coordinator executor. Capture callbacks publish to a one-slot latest-frame mailbox; replacing a waiting packet releases its buffer. One frame processing lease and one render in flight per channel is sufficient for the first implementation. Stop waits for or safely retires in-flight work, tears down that channel and releases its device claim. A stopped/faulted B cannot mutate A's detector, identity, crop, or route.

Hot unplug marks the affected source missing, increments its generation, rejects its pending Take, and exposes fault/reconnect controls. It never auto-binds another camera, switches roles, or changes output destination. If Preview is lost, Program continues. If Program is lost, the router may repeat that channel's last-good **rendered** frame for a short, labelled grace interval (initial policy 2 seconds), then sends an explicit safe standby/black frame at the show format, with visible `Program source missing`; it never exposes raw pixels or takes Preview automatically. Render-only faults use the existing last-good behavior and ownership/HOLD semantics within the same live source generation; a stale last-good from an earlier source generation is not valid after a rebind. Reconnection discovers the device but requires an explicit operator Restart/Reclaim. If the restored channel is still the assigned Program ID, preserve its hold/standby output until a fresh legal render from the new generation is validated, then resume that **same assigned** Program route; no Take to the alternate channel is implied. Preview restoration simply restores Preview eligibility. A Take to the other channel still requires a separate explicit click. An output display/virtual-camera fault is a destination fault, not a reason to swap cameras; do not silently move the Program window to the operator screen or another display. Disable the present route and show its exact endpoint as missing. Reattachment of that exact selected endpoint may resume after format/readiness checks, without rerouting to another endpoint. An intentional Program Display/virtual-camera destination change is allowed only with the show stopped. This replaces the present `DisplayOutputSink` automatic fallback behavior. Stopping the show retires both channel generations, cancels Take, ends the output clock and sends/holds no further frame; the last UI image may remain as a clearly labelled stopped preview, never an active downstream claim.

Configuration changes to show rate or output format require stopping the show. Capture profile/source changes require a safe stop/reconfigure of that channel and invalidate its prepared Preview frame; live-channel changes need the explicit live-edit path and a truthful interruption warning. Persist A/B device preference, source profile, and last output destination for setup convenience, but never persist a live Program/Preview Take state that auto-routes video at launch. Detect duplicate or missing persisted IDs and ask the operator to assign them. Display IDs can change on reconnect; retain the existing guard against covering the operator UI.

## Command and console contract

At gesture creation, bind an `OperatorCommand` to a stable `ChannelID`, origin, unique ID, expiry, that channel's epoch, and the UI control-target revision. Delayed continuations retain that target; they cannot look up “currently selected” at execution. Commands for A do not invalidate B's epoch or zoom; a show-level Stop is distinct and invalidates both. Per-channel deduplication/expiry, recovery ownership, mode restrictions, and existing one-rung ladder remain. Entering/exiting Edit Live or completing a Take cancels pending UI gestures for the former control target, including a pending tap or queued zoom admission; it does not cancel already-admitted ongoing moves in either channel. A discrete mode/preset/lock/rebind change increments the relevant shot revision and invalidates Preview readiness until a new render. `Take` captures the Preview ID/revision at its click; if roles or Preview revision change before the next output tick, it rejects. Two rapid Takes cannot bounce through the same pending click.

The console is one Multiview frame at a minimum window of 1280×800 pt. Wider windows scale the panes proportionally, keeping 16:9 and the 32 pt centre gutter. Every coordinate below is at 1280×800.

A Preview tap is clearly separate from Take. Footer: `Nothing goes to the ATEM until you press Start. Alfie never restores a Program/Preview state from the last show.`

### Input capacity

The R2 technical release ships **exactly two** running inputs (A and B). The console layout reserves **four** fixed input slots (A–D) so the frame never re-flows when inputs are added. Running a third and fourth input is the R2 follow-on set **INPUTS-N / CUE / ADMISSION-N / MULTI-QA-N**, gated on the two-input `MULTI-QA` passing; no build may claim 3–4 input support before that gate. Until then slots C and D render as dashed "not assigned" placeholders and `ChannelID` may declare C and D without instantiating channels for them.

**N-input Preview rule.** With two inputs, Preview is always the other channel. With three or four, Preview is whichever non-Program input the operator (or, in R3, the director) **cues**; cueing never cuts. All tile taps route through a single `ShowCoordinator.cue(ChannelID)` entry point, which R2 implements as a no-op for two inputs; tapping the Program tile shows `Cam A is Program · use Edit Live to change it`.

### Auto Director seam (R3)

The next-shot panel is the only R3 UI slot. The director acts only by cueing Preview and requesting the same Take the operator uses; there is no second output, second Take path or director-only route. `NextShotStatus` carries an optional director section (mode, proposal, reason, countdown, authority) that R2 always leaves nil and never renders. R2 adds no Auto Director controls, disabled or otherwise.

## Scheduler, admission, and degraded operation

Keep one-slot capture and UI preview mailboxes per channel, at most one Vision job and one crop render in flight per channel, and a fixed-size render pool. Initial retention caps are **provisional**: one pending capture packet plus one in-flight source buffer per channel; one latest rendered Preview packet and one last-good rendered packet per channel; at most three render-pool buffers per channel plus the explicitly counted output-sink/current-display retain. These are ownership slots, not an additive memory promise: a buffer can occupy multiple references, and the pool may need tuning against Core Image/compositor behavior. Instrument distinct live IOSurfaces and high-water counts; never expand a pool/queue silently to meet cadence. The static `CropEngine.renderQueue` cannot be the hidden owner of both channels; replace it with an explicit scheduler that chooses only a current mailbox packet. Program gets the next output deadline first; when both have pending work and a render slot becomes free, Preview receives the next fair opportunity within two scheduling selections. An already-running slow GPU render cannot be preempted, so no wall-clock two-frame service guarantee exists; missed freshness is reported, Take stays disabled, and the pair may become unsupported. Perception runs only for relevant tracking/discovery, using the existing bounded ROI/proxy policy, and is fairly admitted between tracking channels. Pan/Manual do not run unnecessary tracking Vision. Composition state is per channel; MainActor occupancy and preview publishing are bounded and measured.

Before enabling B, measure A alone at the requested show rate with its actual device/profile and output route. Admission then probes B with the proposed pair and verifies device coexistence, actual delivered formats/rate, sustained source cadence, render and presentation headroom, memory, and thermal behavior. If the pair cannot sustain the standard, keep A available and label B `Unsupported at this show standard`; do not silently drop the feed to 30 fps. A machine/format pair is `unknown` until measured, `certified` only after the hardware matrix/soak, or `unsupported` when a concrete constraint fails. Unknown may enter an explicitly labelled trial session; it must not be represented as certified. Do not require a specific capture-card model or invent a universal CPU/GPU performance promise.

Track, per channel and output: capture arrival/rate and AVCapture drops; mailbox replacement; MainActor hop and occupancy; Vision queue/wall/observation age; compose/render queue wait and wall time; buffer retention and pool high water; latest render/source age; legal crop; output accepted/presented rate, clock discontinuity, repeated hold/standby ticks; Take request/commit/reject reason and latency; thermal state and RSS. Use bounded/coalesced telemetry, not per-frame published SwiftUI strings or logging. Set actual numeric admission thresholds from R1 metrics and rig runs before release. A 3840×2160 BGRA source frame is roughly 33 MB; count retained source and rendered buffers in the budget rather than assuming “one buffer” in each layer. Record peak and sustained use across a 60-minute run.

Under sustained overload, shed optional UI/diagnostics refresh first, then optional pose/face refresh without weakening identity recovery, then lower background Preview perception within an explicitly measured floor, then reduce Preview preview work while preserving a bounded fresh candidate and a truthful `Preparing` state. Do not reduce the routed output standard, loosen legal crop/identity checks, or allow stale Preview Take. If source ingest or Program deadlines still fail, mark the pair unsupported and keep/restore a single-channel configuration by explicit operator action. Degradation and recovery are hysteretic and reported; no silent quality changes.

## Work units and acceptance

The existing R2 board keys describe one dependency chain. `CHANNEL` remains dependent on `R1-GATE`; this design does not waive that implementation gate. Within `CHANNEL`, use small reviews rather than a new framework: (1) move the single `ProgramOutputManager` into a minimal show-level facade while A retains identical behavior; (2) extract A's per-channel state behind that facade and prove single-channel equivalence; (3) extract capture/configuration and per-channel generation, with off-MainActor blocking calls; (4) instantiate isolated B state with no routing. `ROUTER` extends the minimal facade with packet validation, one output clock and role switching. Preserve current single-camera tests and run output-rate regression after each seam.

| Work unit | Concrete completion evidence |
| --- | --- |
| `CHANNEL` | A-only mode, HOLD, shot ladder, format, render, output and stop/restart match current behavior; A/B state instances cannot share lock/gallery/pan/zoom/last-good. |
| `DEVICES` | Distinct exclusive claims; duplicate ID rejected; A succeeds if B start fails; hot unplug/reconnect does not steal a claim or auto-switch. |
| `CHANNEL-CMD` | Captured target, per-channel epoch/shot revision, delayed completion and Preview-selection race tests; live edit is explicit. |
| `SCHEDULER` | Bounded mailboxes and fair render/Vision opportunities; injected slow B causes visible freshness/admission failure without unbounded queue growth or leaked IOSurface, rather than a false non-blocking guarantee. |
| `ROUTER` | Exactly one sink/output clock, A-only equivalent route, channel-labelled frame packets, old-generation/out-of-order rejection and destination fault handling. |
| `ADMISSION` | Actual two-device/rate/profile probes, unknown/certified/unsupported states, truthful rejection and recorded workload metrics; independent of console/Take. |
| `TAKE` | Single serialized role exchange only on current legal Preview revision and fresh render; two rapid Takes, preset-during-wait, stop/rebind, late old render and output timestamp continuity tested. |
| `CONSOLE` / `TAKE-BAR` / `NEXT-PANEL` / `INPUT-STRIP` / `PILL-TARGET` / `SHOW-SETUP` | At 1280×800 the Multiview frame fits without clipping; Program pane equals output; Preview controls cannot alter Program; explicit live edit; Take and next-shot panel show the same refusal reason; four fixed slots with two filled; accessible role labels. |
| `DEGRADE` | Fault injection and sustained overload reveal bounded shedding, truthful health, no stale Take or silent rate/identity relaxation. |
| `MULTI-QA` | Deterministic fake-clock/device/sink tests plus real hardware matrix and 60-minute two-input soak; source fingerprint, formats, rates, output route, ATEM capture, thermal/memory and faults recorded. |

Gate order: `R1-GATE → CHANNEL → DEVICES/CHANNEL-CMD/SCHEDULER/ROUTER`; `DEVICES + SCHEDULER + PREFLIGHT → ADMISSION`; `ROUTER + CHANNEL-CMD + ADMISSION → TAKE`; `TAKE + CHANNEL-CMD → CONSOLE`; `ADMISSION + READINESS + SCHEDULER → DEGRADE`; `CONSOLE + DEGRADE + R1 SOAK/LATENCY evidence → MULTI-QA`. The R1 gate is an actual dependency for implementation, not merely a release label. No cycle depends on the console to admit hardware.

Use deterministic fakes to replay identical A/B capture sequences and controlled delays, faults and clock ticks; assert pixel identity of the routed channel, exact role state, monotonic output PTS, bounded queue/buffer counts, and independent command/lock states. The real matrix covers at least 50, 59.94 and 60 where both devices claim support, mixed Stage/Webcam resolutions, same and different capture-card families where available, display and virtual-camera routes, hot unplug/reconnect of each input/output, sleep/wake, format mismatch, source PTS reset, and prolonged thermal load. Run 60 minutes with both moving subjects and a human one-hand operator rehearsal; measure rather than assert an unverified zero-drop promise. A configuration is certified only for its tested machine, OS, cards, formats, show standard and route.

Mac App Store work is a separate gate: the platform minimum OS is unresolved, and store distribution, camera-extension compatibility, permission text/privacy treatment, install/upgrade and diagnostics handling need real evidence. This design makes no store approval or universal hardware claim.

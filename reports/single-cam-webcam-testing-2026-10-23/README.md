# Single Cam and built-in camera testing — 23 October 2026

This group follows PR #76 and prioritizes the owner's request to make Single Cam usable and allow the MacBook webcam for multi-camera testing. It covers [SINGLE-CAM](https://trello.com/c/pgwTdM7I), [MODE-SWITCH](https://trello.com/c/fGLSkXF7), [CAPTURE](https://trello.com/c/Ed2ctBWc) and [SHOW-SETUP](https://trello.com/c/ztw0PPkU), with admission and MODE-QA follow-ups. The requested webcam exception is included without creating another ticket.

## Implemented

- Single Cam was already implemented in the source. It retains the traditional source/crop view and all Stage controls. The app now retains one show, derives Camera A from it, and constructs startup observers only through the deferred retained-show factory. ContentView uses the supplied show's A even if a caller supplies a mismatched legacy camera; Settings, controls and output share that ownership by construction.
- Multi Cam stays visible while any attached input is running or starting, including B-only operation after A stops. Traditional Single Cam/Webcam still use A's running state. Observation uses the existing bounded show lifecycle notifications, with no copied live flag or new frame-path publishing.
- A visible **Built-in camera testing** option is available in stopped Multi Cam setup and the Single Cam inspector. It defaults off each app launch, is locked while any input runs/starts, and applies to attached and future channels. Actual AVFoundation device type is rechecked at capture configuration; names and discovery descriptors cannot authorize an external camera.
- Exact native show-rate capture still wins. Only an explicitly enabled system-identified built-in camera gets the new Stage fallback. The actual selected FPS, delivered dimensions and existing crop/freshness rules remain. Its actual capture profile is `stage-built-in-test`, keeping its admission/qualification key separate from ordinary native/Debug captures. A fixed60-only fallback against show50 reports its actual rate and is not falsely labelled below-rate.
- Coarse stored native-format failures or certification do not decide the new built-in test proposal. Conversely, stored test-fallback records cannot masquerade as native history. The live full-fingerprint measurement and all performance refusals remain active.
- Selected local Rehearsal or available Direct output skips irrelevant virtual-camera installation preflight. Virtual output and missing-Direct fallback retain the install gate; command epoch/expiry and post-suspension route checks remain.
- Diagnostic reports use the actual profile for fallback labels. Built-in Stage testing is not called Webcam mode. No production numeric budgets, DeveloperFlags, project settings, entitlements, Info.plist or extension-shared Director dependencies changed.

The [1280×800 setup render](evidence/setup-built-in-test.png) is synthetic gallery evidence, inspected for fit and truthful unknown/test status. Actual manual tests used the final Debug candidate on this Mac with Rehearsal selected. No physical receiver or virtual-camera consumer was used, and no live camera images are committed.

Single Cam started the physical MacBook camera, delivered 1920×1080 at configured 30 fps, and showed approximately 29.5–30 fps. The full Stage controls were visible. Manual, Auto Pan, zoom through the shot ladder, Return to Wide and Stop responded; Stop returned to the Single Cam stopped screen and unlocked the test option. A final native-window visual check confirmed live pixels in both the wide source and program panes. Detect followed by a tap in the source acquired a subject, changed the control to Locked, displayed the subject/crop overlays and rendered the Waist Up crop in Program at about 30 fps. Return to the stopped screen was verified again. This short check did not establish long-running subject-lock correctness, cinematic quality or a full operator rehearsal. Native pixel/crop limits stayed active; lower-rate/lower-resolution test capture does not become a higher-quality source.

Multi Cam then started the built-in input as A with a distinct external input as B. Both produced approximately 30 fps and Preview initially reached Ready. The existing automatic pair check subsequently refused Take: the external input rendered about 29.7 fps against its configured 50 fps, and the short sample reported memory growth around 98 MB/min. That refusal was preserved. No successful manual Take is claimed. Both cameras were explicitly stopped afterward, and the app was left in Single Cam. This is a successful capture/start/stop test with an observed pair-performance failure, not sustained-load or native-rate qualification. Physical built-in-as-B placement remains untested here; both channel placements are covered by deterministic policy/configuration tests.

An earlier manual route mismatch was inconclusive because macOS menu selections were not consistently committed. Final route choices were explicitly committed and rechecked. The shared-owner change is justified and tested structurally; this report does not attribute the earlier ambiguous UI observation to App recreation. Raw native accessibility text is retained only in the temporary artifact folder, separately from the synthetic screenshot.

## Try it

Use the local [Debug test app](/Users/stephanmorris/Documents/macOS-rl-viritual-camera/build/camera-testing-2026-10-23/Debug/Alfie.app) for local rehearsal, or the [unsigned Release candidate](/Users/stephanmorris/Documents/macOS-rl-viritual-camera/build/camera-testing-2026-10-23/Release/Alfie.app) with a valid output route. These copied binaries match their validated products; this does not establish signed installation.

1. While stopped, pick **Single Cam**. In the inspector's Source section select the MacBook camera and turn on **Built-in camera testing**.
2. For local Debug work choose **Rehearsal · no output** in Output settings and commit the menu choice. For real output use the appropriate connected route; virtual-camera installation requirements remain.
3. Start, exercise the controls and Stop. To try two devices, pick **Multi Cam**, assign two distinct devices, enable the same option and start the pair. Live pair limits can still refuse Take; retain the stated reason rather than bypassing it.

The test choice resets when the app quits. Primary tracked source and unrelated user files are untouched; implementation is on `codex/single-cam-webcam-testing`. Real output, signed install, full mode/migration/VoiceOver matrices, sustained load and Director per-level qualification remain open.
